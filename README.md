# Order Flow App Backend（Laravel API）

Order Flow App のバックエンド API リポジトリです。

## 概要

Order Flow App は、店舗で受け付けた注文を管理するための注文管理アプリです。

本リポジトリは、注文作成・注文更新・商品管理・店舗管理・権限制御を行う Laravel API です。

## 作成背景

現職では、商品の注文受付にFAXを使用しており、店舗と製造側の連携に課題がありました。

具体的には、以下のような問題が発生する可能性があります。

- 注文不可の商品を受け付けてしまう
- 製造が間に合わない日時の注文を受け付けてしまう
- 店舗・製造側で注文内容の確認に手間がかかる

これらの注文ミスや確認漏れを防ぐため、注文内容・受け渡し方法・希望日時・ステータスを管理できるアプリとして作成しました。

## 技術スタック

- Laravel 12（API）
- PHP 8.4（Docker / Laravel Sail）
- MySQL
- Laravel Sanctum（認証）

## 主な機能

- 注文の新規作成
- 作成済み注文の更新管理
- 商品の作成・更新・表示状態管理
- 店舗の作成・更新・表示状態管理
- admin / store_user による権限制御
- 店舗ごとの注文閲覧・更新制御
- 注文ステータスによる更新制御
- FormRequest による入力バリデーション

## 権限制御

このアプリでは、Laravel Sanctum による認証を行い、ログインユーザーの role によって操作できる範囲を分けています。

### admin

admin は、注文を受け付ける店舗側ではなく、管理者として以下の操作を行います。

- 商品管理
- 店舗管理
- 注文の更新管理

#### 商品管理

注文フローで使用する商品を管理します。

- 商品の新規作成
- 商品名・価格・画像の更新
- 商品の表示 / 非表示の切り替え

一度登録した商品は、過去の注文データとの整合性を保つため削除せず、非表示機能で注文フローに出さないようにしています。

#### 店舗管理

注文を受け付ける店舗情報を管理します。

- 店舗の新規登録
- 店舗情報の更新
- 店舗の表示 / 非表示の切り替え

商品と同様に、店舗も削除ではなく非表示で管理しています。これにより、過去の注文データと店舗情報のつながりを残せるようにしています。

なお、店舗に紐づく store_user アカウントの作成・紐付けは、現時点では管理画面からは行わず、バックエンド側で設定しています。

今後の改善として、管理画面から店舗ユーザーを発行できるユーザー管理機能を追加予定です。

#### 注文の更新管理

admin は作成済み注文の内容確認・更新を行えます。

ただし、現場の店舗から注文を受け付ける想定のため、admin は新規注文作成を行わない設計にしています。

### store_user

store_user は、店舗で注文を受け付けるユーザーとして、以下の操作を行います。

- 注文の新規作成
- 自店舗の注文更新管理

注文作成では、希望日・希望時間・商品・顧客情報・受け渡し方法などを入力し、店舗での注文受付業務を想定した注文フローを進めます。

注文更新は admin と同様に行えますが、操作できるのは自分の `store_id` と一致する受注店舗の注文のみです。

他店舗の注文は閲覧・更新できないようにし、店舗ごとの注文管理範囲をバックエンド側で制御しています。

## 注文管理機能

作成済みの注文に対して、以下の情報を更新できます。

### 顧客情報の更新

注文に紐づく顧客情報を更新できます。

- 名前
- 住所
- 電話番号

### 商品内容の更新

注文に含まれる商品内容を更新できます。

- 商品の追加
- 数量変更
- 商品の削除

### 受け渡し方法の変更

注文の受け渡し方法を変更できます。

- 店舗受取から配達への切り替え
- 配達から店舗受取への切り替え
- 受取店舗の変更
- 配達先住所の変更

店舗受取から配達へ切り替える場合は、不要になった受取店舗情報を削除し、配達情報のみが残るようにしています。
反対に、配達から店舗受取へ切り替える場合も、不要になった配達情報を削除し、受け渡し方法に応じた情報だけを保持する設計にしています。

### 希望日時の変更

希望日は、現在日から2日後以降の日付のみ指定できます。

注文作成時だけでなく、注文更新時にも同じ制約を適用し、更新画面から不正な日付が登録されないようにしています。

### 注文ステータス管理

注文ステータスは以下の状態で管理しています。

- 受注
- キャンセル
- 完了

注文ステータスに応じて更新可能な操作を制御し、キャンセル済み・完了済みの注文が後から変更されないようにしています。
この制御は Controller 側の条件分岐だけに寄せず、Laravel Policy で管理しています。  
そのため、どの更新APIからアクセスされた場合でも、注文ステータスに応じた更新可否を一貫して判定できるようにしています。

## バリデーション・業務ルール

注文作成時には、Laravel の FormRequest を使用して入力値を検証しています。

基本的な形式チェックに加えて、実際の店舗業務で起こりうるミスを防ぐため、以下のような業務ルールもバックエンド側で制御しています。

- 希望日は2日後以降のみ指定可能
- 受け取り時間・配達時間は、開始時間が終了時間より前になるように制御
- 存在しない商品IDで注文できないように制御
- 電話番号は10〜11桁の数字に制限
- 郵便番号は7桁の数字に制限
- 停止中の店舗は注文フローで選択不可

## データ構造・整合性

注文作成時には、主に以下のテーブルに情報を保存しています。

- `customers`：注文者の氏名・住所・電話番号
- `orders`：注文日時・希望日・希望時間・受け渡し方法・受取店舗・配達先情報・注文ステータス・合計金額
- `order_items`：注文された商品・数量・注文時点の商品価格

注文者情報、注文本体、注文商品をテーブルごとに分けることで、注文内容を管理しやすい構造にしています。

また、注文作成処理では、`customers`、`orders`、`order_items` をまとめて保存するため、トランザクションを使用しています。

これにより、注文作成の途中でエラーが発生した場合でも、顧客情報だけ保存される、注文本体だけ保存される、商品明細だけ保存されないといったデータ不整合を防いでいます。

## セットアップ（ローカル環境 / Laravel Sail）

```bash
cp .env.example .env
composer install
./vendor/bin/sail up -d
./vendor/bin/sail artisan key:generate
./vendor/bin/sail artisan migrate --seed
```
